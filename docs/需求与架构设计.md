## 第一步　需求深挖

### 1.1 一句话需求

在**中小型自营商城现有商品、订单、物流、售后 API 之上**，增加一层自然语言服务入口，覆盖「导购 → 订单查询 → 售后预审 → 政策问答」四类高频诉求，且所有写操作可控、可审计、可回归。

### 1.2 显性需求（用户说出来的）

| # | 需求 | 来源角色 |
|---|---|---|
| R1 | 用户用自然语言描述预算/场景/偏好，能得到 3 个候选商品与推荐理由 | 消费者 |
| R2 | 能查询自己的订单与物流，不需要在多系统间切换 | 消费者、客服 |
| R3 | 能发起退换货申请，并知道是否具备资格、依据是什么 | 消费者 |
| R4 | 政策类问题（运费、保修、发票、退换时限）有确定答案并可查出处 | 消费者、客服 |
| R5 | 复杂或高风险会话能转人工，客服拿到上下文而不是从零问起 | 客服 |
| R6 | 系统上线后检索与回答效果可量化，不靠感觉 | 商品运营、主管 |

### 1.3 隐性需求（用户没说但必须满足）

| # | 隐性需求 | 不满足的后果 |
|---|---|---|
| H1 | 价格/库存必须是**实时**的，不能来自知识库快照 | 用户下单发现价格不符，产生投诉 |
| H2 | 退款资格与金额**不能由模型自由裁决** | 错误放行率失控，财务与合规风险 |
| H3 | 同一退款不能提交两次 | 重复退款，资金损失 |
| H4 | 消费者不能查到别人的订单 | 越权与隐私事故 |
| H5 | 模型被诱导（prompt injection）不能提权 | 越权退款、数据泄露 |
| H6 | 模型/向量库/库存 API 故障时系统不能整体不可用 | 大促期间客服不可用 |
| H7 | 每个回答要能回溯到证据与版本 | 政策过期无法追责 |
| H8 | 回答延迟要可感知地低（流式） | 用户等待超时直接转人工，成本上升 |
| H9 | 评测集与指标可复现，能对外解释口径 | 简历/汇报数字站不住 |

### 1.4 角色—场景—需求矩阵

| 场景 | 消费者 | 客服 | 主管 | 运营 |
|---|---|---|---|---|
| 导购咨询 | R1 | 辅助 | — | 查看 Bad Case |
| 订单/物流 | R2 | R2 全量 | — | — |
| 售后申请 | R3 | 接管 R5 | 高价值审批 | 规则配置 |
| 政策问答 | R4 | R4 加速 | — | 知识维护 |
| 效果治理 | — | 抽检 | R6 看板 | R6 评测 |

### 1.5 需求优先级（MoSCoW）

| 级别 | 内容 | 说明 |
|---|---|---|
| **P0 必须有** | 意图路由、混合检索、订单鉴权、售后规则引擎、写操作确认+幂等、引用溯源、降级、离线评测 | 缺任何一项，闭环不成立或不可防守 |
| **P1 应该有** | 人工接管包、SSE 流式、Trace 串联、Bad Case 记录、单测覆盖 | 决定「像不像工程」 |
| **P2 可以有** | 少量 MCP 只读工具、评测台前端页面、文案合规流水线 | 加分项，不牺牲 P0 |
| **P3 明确不做** | 训练推荐模型、真实支付、自动审批退款、跨企业 A2A 网络 | 超出 PoC 边界 |

### 1.6 可验收的需求边界（DoD）

- 四条主流程各自具备**正常 / 失败 / 接管**三条路径。
- 危险写操作**未确认执行次数 = 0**；同一逻辑操作重复提交**只产生 1 条记录**。
- 越权查询在**工具层**被拒绝，界面不泄露「订单是否存在」。
- 政策类回答 100% 带 `doc_id + 版本 + 生效日期`；无证据时明确拒答。
- 指标来自可复现脚本：意图 Macro-F1、检索 Recall@10/NDCG@10、引用准确率、拒答准确率、P95 与 TTFT。

## 第二步　痛点分析

### 2.1 业务痛点 → 技术归因 → 解决手段

| # | 业务痛点（现象） | 技术归因 | 本项目的解法 | 验证方式 |
|---|---|---|---|---|
| P1 | 用户说「2000 内通勤降噪、戴眼镜不夹头」搜不到合适商品 | 关键词检索无法表达软偏好；纯向量又忽略硬约束 | 结构化硬过滤 → BM25 + 向量双路召回 → RRF → Reranker | Recall@10 / NDCG@10 + Bad Case |
| P2 | 客服要开 4–5 个系统才能答一个问题 | 能力散落在商品/订单/物流/售后，无统一入口 | 工具网关统一封装 8 个工具 + 编排层按意图路由 | 端到端流程时延与步数统计 |
| P3 | 退了不该退的、退了两次 | 资格判断靠人；提交无幂等 | 版本化规则引擎判资格 + 幂等键 + 乐观锁版本校验 | 安全用例集（越权/重复/过期规则） |
| P4 | 政策讲了但和实际不符（运费、时限） | 政策过期、无版本、回答无出处 | 切块携带 version/effective_at/authority，回答强制引用 | 引用准确率 ≥ 95% |
| P5 | 用户投诉「机器人乱承诺有货/有优惠」 | 价格库存来自缓存或知识库 | 实时工具读取 + 查询时间标注 + 失败不承诺 | 降级用例 |
| P6 | 模型被一句「忽略规则」骗去调用退款 | 把 Prompt 当权限边界 | 身份注入 + 工具白名单 + Schema 校验 + 规则裁决 | Prompt Injection 用例 |
| P7 | 效果无法证明，只能说「感觉更准了」 | 没有标注集与指标口径 | 自建标注集 + 固定脚本 + 报告落库 | eval 报告可复跑 |
| P8 | 模型挂了整条链路不可用 | 单点强依赖 | 分级降级矩阵（模型/向量/库存/SSE） | 故障注入测试 |

### 2.2 痛点优先级判定

按「发生后损失 × 发生概率」排序：**P3（错退/重退）> P4（政策错答）> P6（越权）> P5（虚假承诺）> P1（搜不准）> P2（效率）> P7/P8（治理与可用性）**。

这一排序直接决定实现顺序：**先做规则与安全，再做检索质量，最后做体验优化**——与第十步排期的优先级一致。

## 第三步　复杂项目拆分为流程

### 3.1 L0 主干（一次完整会话）

```
接入鉴权 → 意图识别 → 槽位抽取 → 分支执行 → 结果组装 → 流式返回
                 ↑                              ↓
             人工接管 ←────────────── 失败/高风险
```

### 3.2 L1 七条流程

| 编号 | 流程 | 输入 | 输出 | 是否含写操作 |
|---|---|---|---|---|
| F1 | 会话接入与鉴权 | JWT、消息 | user_id/role/trace_id | 否 |
| F2 | 意图识别与槽位抽取 | 消息+历史摘要 | intent、slots、缺槽位 | 否 |
| F3 | 商品混合检索与导购 | 品类/预算/偏好 | 3 候选+理由+引用 | 否 |
| F4 | 订单与物流查询 | 订单号/自然语言指代 | 脱敏订单卡片 | 否 |
| F5 | 售后预审与提交 | 订单、原因、证据 | 草稿/提交结果/转人工 | **是** |
| F6 | 政策知识问答 | 问题 | 带引用回答/拒答 | 否 |
| F7 | 人工接管与治理 | 触发条件 | 接管包、审计、Bad Case | **是（内部）** |

### 3.3 L2 关键子步骤

- **F1**：JWT 解析 → 角色映射 → 限流 → trace_id 注入。
- **F2**：LLM 分类（有 Key）/ 规则分类（无 Key）→ 槽位抽取 → 缺槽判断（最多澄清 2 轮）。
- **F3**：硬过滤（类目/价格/库存/状态）→ BM25 top-k → 向量 top-k → RRF → Reranker → 实时价格库存补充 → 生成 3 候选。
- **F4**：订单号格式校验 → 归属校验 → 订单+物流并行查询 → 字段脱敏 → 卡片化。
- **F5**：订单状态校验 → 规则引擎（时限/品类/签收/金额）→ 生成草稿 → 用户确认 → 幂等提交 → 审计。
- **F6**：query 改写 → 混合检索（政策域）→ 证据充分性判断 → 带引用生成 → 实体存在性校验。
- **F7**：触发判定 → 打包上下文 → 落库 → 客服端状态流转 → 事后 Bad Case 标注。

## 第四步　项目难点分析

| # | 难点 | 为什么难 | 方案 | 如何验证 |
|---|---|---|---|---|
| D1 | **概率能力与确定能力边界** | 模型擅长理解、不擅长裁决；两者混在一处就既不可测也不可审 | 意图/槽位/改写交 LLM；鉴权/状态/金额/幂等交确定性节点 | 状态机单测 + 安全用例 |
| D2 | **混合检索的分数融合** | BM25 与向量分数量纲不同，直接加权不稳定 | RRF 按排名融合（k=60），再叠加 Reranker 与业务分 | Recall@10 / NDCG@10 对比 BM25 |
| D3 | **硬约束 vs 语义偏好共存** | 向量相似不保证在预算/库存内 | 先 SQL 硬过滤缩小候选，再语义排序；实时字段最后补 | 约束违反率 = 0 用例 |
| D4 | **写操作幂等与并发** | 网络重试、多端点击、状态并发变更 | Idempotency-Key 唯一约束 + 订单 version 乐观锁 + 事务 | 重复提交用例、版本冲突用例 |
| D5 | **越权与注入防护** | 模型参数不可信，检索内容不可信 | user_id 服务端注入、工具白名单、Pydantic 严格校验、指令与数据分隔 | 越权/注入用例 |
| D6 | **政策时效与引用溯源** | 政策会改版，模型会「顺口编」 | 切块带 version/effective_at/authority；回答强制引用；无证据拒答 | 引用准确率、拒答准确率 |
| D7 | **多级降级** | 任一依赖故障都可能拖垮全链路 | 模型→模板、向量→BM25、库存→不承诺、SSE→可取消 | 故障注入用例 |
| D8 | **评测可信度** | 自动指标易被 Judge 偏差放大 | 固定标注集 + 固定脚本 + 人工引用核验 + Bad Case 归因 | 报告可复跑、口径写明 |
| D9 | **两天数万 SKU 的检索性能** | 逐条 Python 打分在 1 万 SKU 上会拖慢响应 | 预构建稀疏矩阵 + numpy 批量余弦 + 候选集裁剪 | 压测 P95（固定环境） |
| D10 | **BGE-M3 本地加载** | 模型 2GB+，国内网络易失败；加载慢 | 单例懒加载 + HF 镜像 + 失败自动降级哈希向量并显式标注 | 启动日志 + `/api/health` 反映模式 |

## 第五步　根据难点复审第三步的流程

> 这一节不是重写流程，而是把难点「回灌」成流程上的具体约束。

### 5.1 流程变更表

| 受影响流程 | 复审发现的问题 | 变更 |
|---|---|---|
| F1 | 原流程未在入口固定身份，模型参数中可能夹带 user_id | 鉴权提前为**第一个节点**，`user_id` 只从 Token 注入，状态中不接受外部传入 |
| F2 | 澄清无上限会陷入死循环 | 明确「最多 2 轮澄清」，超出转人工；`retry_count` 与最大步数上限 |
| F3 | 原设计「先召回后过滤」会返回超预算商品 | 顺序改为**硬过滤 → 双路召回 → RRF → 精排 → 实时补充** |
| F3 | 库存/价格可能被写进回答模板造成虚假承诺 | 实时字段只来自 `get_live_offer`，回答标注查询时间；失败不承诺 |
| F4 | 越权查询若在编排层判断，模型可绕过 | 归属校验下沉到**工具层 + SQL 层**双重校验；失败返回统一拒答，不区分「不存在/无权限」 |
| F5 | 规则版本可能在提交时已失效 | 提交前校验 `rule_version` 仍生效 + 订单 `version` 未变 + 幂等键未成功 |
| F5 | 高风险（高价值/特殊品类）不应由模型或普通客服放行 | 增加主管审批节点，`risk_level=high` 强制转审批 |
| F6 | 检索命中但证据不足时仍会生成 | 增加**证据充分性判定节点**，不足则拒答并给政策链接 |
| F7 | 原「转人工」只是一句提示，客服仍需重问 | 接管包结构化落库：意图/槽位/工具结果/失败原因/风险标签/摘要 |
| 全局 | 任一节点异常会中断整条链路 | 每个节点输入输出 Schema 固定，异常进 `error` 状态并由条件边分流到降级/接管 |

### 5.2 复审后的节点清单（最终版）

| 节点 | 类型 | 确定性 | 说明 |
|---|---|---|---|
| `authenticate` | 网关 | 是 | JWT → user_id/role |
| `classify_intent` | LLM/规则 | 概率 | 6 类 + unsafe/unknown |
| `extract_slots` | LLM/规则 | 概率 | 品类/预算/偏好/订单号/原因 |
| `clarify` | 模板 | 是 | 最多 2 轮，缺槽位追问 |
| `retrieve_products` | 检索 | 是 | 硬过滤 + BM25 + 向量 + RRF |
| `rerank_products` | 模型/启发式 | 半 | Reranker + 业务分（可解释权重） |
| `live_enrich` | 工具 | 是 | 实时价/库存/促销资格 |
| `ownership_check` | 规则 | 是 | 工具层强制归属 |
| `query_order` / `query_logistics` | 工具 | 是 | 脱敏返回 |
| `policy_rag` | 检索+生成 | 半 | 引用 + 证据充分性 |
| `evaluate_after_sale` | 规则引擎 | 是 | 纯函数、可单测 |
| `prepare_draft` | 规则 | 是 | 生成草稿与风险等级 |
| `ask_confirm` | 交互 | 是 | 中断等待确认（HitL） |
| `idempotent_execute` | 规则 | 是 | 幂等键 + 版本校验 + 事务 |
| `handoff` | 工具 | 是 | 接管包落库 |
| `audit` | 观测 | 是 | trace/工具/耗时/token |

## 第六步　流程串联为业务闭环

### 6.1 端到端闭环（一次会话的完整生命周期）

```
用户 → [F1 鉴权] → [F2 意图/槽位] ─┬→ F3 导购闭环 ─┐
                                   ├→ F4 订单闭环 ─┤
                                   ├→ F5 售后闭环 ─┼→ 统一响应契约 → SSE → 前端
                                   └→ F6 政策闭环 ─┘
                                            ↓ 异常/高风险
                                    [F7 接管 + 审计 + Bad Case]
                                            ↓ 标注与复测
                                    [评测报告] → 反哺检索权重/规则版本/提示词
```

**闭环的关键是最后那条回流箭头**：接管与 Bad Case 不是终点，而是下一轮检索权重、规则版本与提示词迭代的输入。没有回流，系统只会「跑通」，不会「变好」。

### 6.2 三个闭环各自的收敛条件

| 闭环 | 起点 | 终点 | 收敛判据 |
|---|---|---|---|
| 交易咨询闭环 | 用户描述需求 | 用户选定候选/进入下单链接 | 3 候选含实时价库存+理由+引用 |
| 售后闭环 | 用户提出退换 | 草稿确认提交 或 转人工 | 资格依据可查、幂等生效、金额来自规则 |
| 治理闭环 | 接管/差评/Bad Case | 规则或检索策略更新 | 复测指标不劣化，用例进入回归集 |

### 6.3 状态流转（售后为例）

```
CREATED → DRAFTED → AWAIT_CONFIRM → SUBMITTED → (APPROVED | REJECTED | HANDOFF)
              ↑                          ↓
         版本失效/规则变更 ←── CONFLICT（订单状态或规则版本变化）
```

## 第七步　检查整个流程：对照需求与痛点的缺口修正

### 7.1 缺口清单

| # | 检查发现 | 关联需求/痛点 | 修正动作 |
|---|---|---|---|
| G1 | 原流程只有「检索」没有「空结果」处置 | R1、P1 | 增加空召回分支：放宽软偏好 → 提示替代类目 → 转人工 |
| G2 | 售后流程缺「证据不足」的中间态 | R3、P3 | 增加 `EVIDENCE_NEEDED` 态，可续传图片/凭证 |
| G3 | 政策问答未校验「文档是否适用于当前品类」 | R4、P4 | 检索时按 `category` 过滤，元数据缺失则该文档不参与回答 |
| G4 | 未明确「同一用户多会话并发」的记忆隔离 | H4 | Checkpointer 键 = tenant+user+thread，服务端校验归属 |
| G5 | 未定义「模型不可用时的 FAQ 兜底内容」 | H6、P8 | 预置审核过的模板 FAQ（运费/时效/保修），故障时命中模板 |
| G6 | 评测只覆盖成功样本 | R6、P7 | 增加负样本：模糊意图、越权、过期规则、无证据、注入 |
| G7 | 前端只展示文本，用户无法确认写操作 | H3、P3 | 确认弹窗展示「订单号/商品/金额/规则依据」，确认后按钮锁定 |
| G8 | 无「已接管」对用户侧的可见状态 | R5 | 前端显示接管状态与客服接入提示，避免用户重复提交 |
| G9 | 缺少「知识版本变更后缓存失效」 | P4 | 缓存键含 `knowledge_version`，版本更新主动失效 |
| G10 | 检索权重不可解释，运营不敢用 | P1、R6 | 业务分权重显式配置并在候选卡上标注「因库存/销量加权」 |

修正后流程满足：**每条主流程都有失败态、每个写操作都有确认与幂等、每个回答都有出处或明确拒答、每次接管都有结构化交接**。

### 7.2 修正后的流程完整性自检

### 8.2 相对原文档的两处工程化调整（PoC 适配，均已在代码中可替换）

| 原方案 | 实际实现 | 原因 | 可替换性 |
|---|---|---|---|
| PostgreSQL + pgvector | SQLite + 稀疏矩阵 BM25 + numpy 余弦 | 免装数据库服务，一条命令启动 | `app/db/base.py` 提供引擎抽象，换 PG 只改连接串与向量适配器 |
| Redis | 进程内 TTL 缓存 + 内存检查点 | 免装 Redis 服务 | `app/core/cache.py` 保持 Redis 同签名接口 |
